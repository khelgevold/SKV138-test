# SKV138 – erfaringer med innlogging, Neon Auth og installert iPhone-webapp
Oppdatert 19.11.2026. **Gjeldende TEST-løsning er brukerbekreftet fungerende.** Dette er teknisk overlevering for å unngå å gjenta feilene ved PROD-etablering.

## Miljø og hovedarkitektur
- Repo `khelgevold/SKV138-test`, gren `feature/neon-test-integration`; TEST `https://skv138-neon-test.netlify.app`.
- `main` inneholder godkjent V16.23 og er ikke endret. Eget PROD-miljø er ikke opprettet.
- Netlify: base `/`, build `npm run build:auth`, publish `backend-draft/test-site`, functions `backend-draft/netlify-functions`. Netlify auto-build kan være aktiv; ikke anta at den er stoppet.
- Ytre innloggingsside `backend-draft/test-site/index.html` viser etter backend-godkjenning hytteappen i sandboxet iframe `app.html`. Auth-klient: `neon-auth-bootstrap.mjs`, `neon-test-entry.mjs`, `login-controller.mjs`, `neon-test-config.mjs`; API-klient `client-adapter.mjs`; server `skv138-state.mjs`.
- Nettleseren autentiserer mot Neon Better Auth og henter kortvarig JWT; backend krever Bearer-token, verifiserer JWKS-signatur (EdDSA), issuer og eventuelt audience, og sjekker `public.skv138_access`. Innlogging alene gir **ikke** rett til appdata. API har GET/PUT, servervalidering, origin-sjekk på PUT og versjonskontroll.
- Ikke legg databasepassord, JWT, hemmelige nøkler eller private connection strings i frontend/repo.

## Faktisk feilhistorikk og hva som fungerte
1. **PC-login stoppet etter synlig innlogging.** Network viste at `GET /neondb/auth/get-j-w-t-token` ga HTTP 404. Neon JWKS (Ed25519/EdDSA), Auth URL og trusted origin var undersøkt. Flere JWT-helper-/session-token-fallbacks ble forsøkt uten å løse problemet. Fungerende TEST-flyt: `authClient.token()`, og ved manglende token direkte `GET {AUTH_URL}/token` med `credentials:"include"`; commits `d173b9e`, `75fe6c4`. Brukeren bekreftet PC-innlogging. Ikke gjeninnfør uverifiserte `getJWTToken()`- eller `session.access_token`-antakelser.
2. **F5 viste login og mistet valgt fane.** `neon-test-entry.mjs` gjenoppretter sesjon med `login.session()` og autoriserer på nytt gjennom backend GET; den hindrer at automatisk restore og manuell sign-in starter to samtidige state-broer. `index.html` skjuler login mens restore pågår. Valgt hovedfane huskes i `sessionStorage`. F01 godkjent på PC.
3. **Installert iPhone-PWA feilet, Safari på samme telefon og PC fungerte.** Diagnostikk bl.a. `TEST_DIAG_TOKEN_EXCEPTION` og `TEST_DIAG_TOKEN_ENDPOINT_HTTP_401`. Feilen fortsatte etter lukking og sletting/ny installasjon av PWA, så ren reinstallasjon var ikke løsningen. Sterk teknisk forklaring var at cross-site cookies mot separat `*.neonauth.*.aws.neon.tech` ble blokkert i installert iOS-webapp. **Ikke bevist isolert som eneste rotårsak**, men same-origin-løsningen løste det i praksis.
4. **Fungerende PWA-løsning:** Nettleserens offentlige Auth URL i `neon-test-config.mjs` er `https://skv138-neon-test.netlify.app/neondb/auth` (commit `6088cfb`). `backend-draft/test-site/_redirects` proxier **hele** `/neondb/auth/*` til Neon managed Auth med HTTP 200 rewrite (commit `7a6264c`). Dermed går sign-in, get-session og /token via appens eget domene; ikke proxy bare token-endepunktet. Kontrakttest for URL/redirect i `test-site-contract.test.mjs` (commit `0ba684f`). Etter publisering bekreftet bruker at installert iPhone-PWA logger inn og åpner appen. Backend JWT-verifisering og allowlist ble beholdt.
5. **Hvit statuslinje over mørk app i installert iPhone-PWA.** Ytre `index.html` hadde lys bakgrunn og manglet iOS-metadata. Commit `64d630a` la inn `theme-color=#101f1a`, `apple-mobile-web-app-capable=yes`, `apple-mobile-web-app-status-bar-style=black-translucent` og mørk `body.app-ready`-bakgrunn. Etter Netlify Published og lukking/åpning av installert PWA bekreftet bruker F06 godkjent. Dette er en visuell endring, ikke auth-endring.
6. **Andre QA-funn:** F03 kansellering ga tidligere 409 ved lagring, men senere brukerprøve og sluttkontroll bekreftet kansellering og økonomitall uten ytterligere endring; årsak til den opprinnelige konflikten er ikke sikkert påvist. F04 plattformgebyrknapper hadde ødelagte inline HTML `onclick`-argumenter grunnet uescapede JSON-anførselstegn; commit `8eed144` HTML-escaper argumentene. F05 fire økonomikort godkjent. Alle F01–F06 og 3/3 sluttkontroller godkjent 19.11.2026.

## Viktige PROD-feller
- **Ikke kopier TEST Auth URL til PROD.** PROD må ha egen korrekt offentlig app-origin, egen same-origin Auth-URL og tilsvarende Netlify rewrite mot riktig Neon Auth-instans. Konfigurasjonen er i dag hardkodet til TEST-domenet; vurder miljøspesifikk konfigurasjon før PROD. Kontroller Neon trusted origin, cookie-path/domain og faktiske sign-in/get-session/token-kall på PROD.
- Opprett **separat PROD-database og Auth/tilgangskonfigurasjon**. Brukeren har eksplisitt besluttet at PROD skal **starte tomt**; ingen TEST-bookinger eller andre TEST-data skal migreres. Avklar opprettelse av nødvendige tabeller/struktur og godkjente brukerkontoer separat, uten å kopiere TEST-data.
- Hold `SKV138_APP_ORIGIN` eksakt lik PROD-origin, uten avsluttende skråstrek hvis requestens Origin ikke har den. Konfigurer `DATABASE_URL`, `NEON_AUTH_JWKS_URL`, `NEON_AUTH_ISSUER`, ev. `NEON_AUTH_AUDIENCE` i Netlify miljøvariabler, aldri i repo.
- Ikke svekk `jwtVerify`, `skv138_access`, origin-sjekk, servervalidering, `expectedVersion` eller database-transaksjoner for å «fikse» login/409. Undersøk reelle feilsvar først.
- TEST-koden har fortsatt `TEST_DIAG_...`-feilkoder og TEST-only JWT-diagnostikk, samt gamle kommentarer om «not deployed»; vurder begrenset opprydding før PROD. Ikke fjern nødvendig feilhåndtering ukritisk.
- Verifiser installert iPhone-PWA på **PROD-domenet** separat etter oppsett. PWA på ett domene beviser ikke at cookies fungerer på et annet. Test PC-login, iPhone Safari, installert PWA, F5/session, én booking og varig lagring; unngå å repetere hele TEST-QA.
- Ingen produksjonsdeploy, databasemigrering eller irreversible handlinger uten brukerens eksplisitte godkjenning. Planlegg backup/rollback før reelle data tas i bruk.
